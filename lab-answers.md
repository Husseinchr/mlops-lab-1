## Question 2

`dvc init` created the following DVC repository files:

- `.dvc/config`: the repository-level DVC configuration. It is initially empty and later stores non-secret settings such as the remote name and URL.
- `.dvc/.gitignore`: prevents DVC's local cache, temporary files, and `config.local` from being tracked by Git.
- `.dvcignore`: lets DVC skip paths that are irrelevant to data tracking, similarly to how `.gitignore` works for Git.
- `.dvc/tmp/`: runtime state used internally by DVC. It is local and ignored by Git.

The files that describe the shared project configuration—`.dvc/config`, `.dvc/.gitignore`, and `.dvcignore`—should be pushed to Git. DVC cache files, temporary files, and `.dvc/config.local` should not be pushed.

## Question 3

Because the authentication commands used `--local`, the username, authentication method, and password are stored in `.dvc/config.local`. DVC automatically ignores this file through `.dvc/.gitignore`.

DVC configuration has four useful scopes:

- No scope option: repository scope, stored in `.dvc/config` and normally committed.
- `--local`: repository-specific private settings in `.dvc/config.local`.
- `--global`: settings for the current operating-system user, outside the repository.
- `--system`: machine-wide settings for all users.

Credentials must not be pushed to GitHub. Only the non-secret remote URL and default-remote setting belong in `.dvc/config`. A fresh clone therefore needs its own credentials supplied locally or through an equivalent secure mechanism.

## Question 4

After `dvc add data`, DVC added `/data` to the repository's `.gitignore`. This prevents Git from storing the image files directly. DVC copied the content into its content-addressed local cache and generated a small Git-trackable pointer file instead. This division keeps source code and metadata in Git while DVC versions the large dataset.

The Python-specific entries `.venv/`, `__pycache__/`, and `*.py[cod]` were also added so local environments and generated bytecode do not pollute the repository.

## Data preparation

The preparation program is `src/food11/data.py`. It follows the class-directory layout expected by [`torchvision.datasets.ImageFolder`](https://docs.pytorch.org/vision/stable/generated/torchvision.datasets.ImageFolder.html), which is commonly used with ResNet image-classification workflows.

The script performs the following deterministic steps:

1. Reads each image label from the numeric prefix in its filename.
2. Maps labels `0` through `10` to the eleven Food-11 class names.
3. Resizes every image to 128×128 pixels using high-quality Lanczos resampling.
4. Writes the complete class-folder dataset to `data/food11_processed`.
5. Writes at most 100 images per class per split to `data/food11_processed_mini`.

The resulting counts are:

| Split | Raw | Processed | Mini |
|---|---:|---:|---:|
| Training | 9,866 | 9,866 | 1,100 |
| Evaluation | 3,347 | 3,347 | 1,096 |
| Validation | 3,430 | 3,430 | 1,096 |
| **Total** | **16,643** | **16,643** | **3,292** |

These are the original Lab 1 counts. Lab 5's leakage check subsequently found cross-split duplicates, so processed outputs were corrected while the raw files were preserved. The current full processed counts are 9,866 training, 3,098 evaluation and 3,068 validation (16,032 total). The mini counts remain 1,100, 1,096 and 1,096 (3,292 total). Both current datasets pass the class-folder, RGB/128×128, minimum-count, cross-split-hash and class-balance checks. The corrected DVC snapshot contains 35,967 files with hash `196ffd5fd3afbb295705e0d0893a9dc1.dir`.
